# Cross-provider execution

`provider/CrossProviderAgentBridge.ts` is the server-lifetime owner of hidden child sessions. `ProviderService` routes authenticated MCP operations, adapter events, and existing task controls through it. The six `t3_agent_*` tools share the Agent Browser access gate and provider-session credentials. There is no second client roster or separate wire protocol.

## Identity and persistence

A public `cross-provider:<uuid>` identifies the durable visible agent. Hidden adapter session IDs can rotate independently during recovery so late events from an old process cannot alter the new execution. The bridge retains the visible root, immediate bridge parent, configured instance, and exact current adapter identity. Hidden sessions are excluded from normal session listings. `CrossProviderAgentRecovery` stores a schema-validated recovery record in the existing provider directory under a stable hidden binding, without a second database or migration. Children inherit the original workspace, runtime mode, and interaction mode; target model selections must name the target instance.

Runtime events are mapped to the visible root with `bridgeAgentId` identifying the wrapper and `agentId` identifying the actual speaker. Native child/task IDs, item IDs, tool links, and request IDs are namespaced. Child lifecycle and diff events cannot change the root session, turn, or checkpoints. Semantic plan, compaction, error, usage, request, and transcript events keep their ordinary types. Request routes retain native IDs and send responses to the hidden adapter session, not the root's current provider.

The existing decider/projector writes authoritative `task.state` records with `executionOwner: "cross-provider"`. Root session transitions exclude these independently owned tasks. Transcripts persist normally. Startup queries indexed current task/control records, marks lost executions interrupted, preserves Resume for wrappers with a matching nondeleted recovery record, and cancels stale native requests. It does not hydrate transcripts or start provider work. The bridge lazily restores the same public ID on explicit access, checking root ownership.

The recovery record is saved before dispatch, at turn boundaries, and on stop, close, and resume. Item-level context is journaled in memory between those writes rather than rewriting the record per tool call. It contains the original assignment, latest input, native cursor, permission/model settings, manual-stop latch, last reply, and a bounded 64,000-character context journal. Writes are serialized per child. Native resume is preferred; known missing-conversation failures allow one fresh-session fallback in the same activation, with an explicit transcript notice and a prompt requiring verification of prior side effects. Allocation of a cursor before any accepted turn is not treated as proof of durable native history.

## Lifetime and control

Accepted launches fork into the provider-service scope, not the HTTP request, parent wait, or parent provider process. Stop and dispatch fences prevent queued or delayed work from running after a user stop. Adapter replacement retires only children owned by that exact adapter. Recovery bindings are excluded from ordinary inactivity reaping; account cleanup asks the bridge to stop its current execution IDs for that instance, including rotated IDs. Closing a child preserves independent descendants; explicit thread deletion disposes the owned tree. Archiving does not imply cancellation. Environment shutdown stops all adapters.

Interrupt scope lives in `ProviderService`, not in adapters. Every adapter keeps its ordinary `interruptTurn`, which stops the selected session together with the native descendants that session owns; bridge children are separate adapter sessions and are never reached that way. Unscoped legacy interrupts default to `self`, which is exactly that adapter interrupt. `scope: "tree"` additionally asks the bridge to fence every child of the root before attempting bounded shutdowns in parallel, independently of the main provider. A failed `self` stop only reports the failure; a failed `tree` stop on a running root falls back to `stopSession` so a wedged provider always has an exit. Unconfirmed child shutdowns retain their ownership and capacity for retry. `supportsInputSteering` permits immediate busy-child delivery; other inputs use bounded per-child queues. `crossProviderAgents: false` excludes externally hosted OpenCode configurations. Clients offer Stop all only while a cross-provider child is live, since a plain Stop already covers everything else the thread owns.

Manual child stops clear queues and persist a stop latch; only the user task-resume command clears it. Root manual-stop intent is also stored in its binding's runtime payload, preventing server-update continuation. Resuming one child does not clear other children's latches. Cancellation and stop-journal writes run independently with deadlines, so a persistence failure cannot prevent the provider cancellation attempt; failures are reported rather than claiming durable confirmation. Questions answered by follow-up message are resolved only after adapter acceptance, not queue insertion. Cancellations carry an explicit marker instead of pretending that empty answers were submitted.

An authenticated child can send to its immediate bridge parent or use the reserved `parent` recipient for the visible root. Root messages are queued into its next real input, including after a manual user resume. Descendant ownership is required for interruption, close, and ordinary target sends. Sibling permission grants are not implemented; sibling operations are rejected.

Preview credentials retain the child's provider-session identity and synthetic thread while carrying an optional `visibleThreadId`. Only preview invocation maps that thread back to the visible root. Parent credential revocation therefore does not revoke child tools. Every child input, including live steering, refreshes its MCP activity timestamp.

Limits are eight open children per root, 32 per environment, three bridge levels, 32 pending messages per recipient, and waits of at most 60 seconds. Server-lifetime request-key receipts deduplicate writes, reject changed arguments, and prevent duplicate accepted launches on retry. Each accepted operation has a service-owned worker; provider I/O does not hold a global write lock. In-memory child records and retry receipts have finite capacities. Limits are explicit errors, not eviction of live execution.

## Boundaries

The stable T3 ID survives process replacement and server restart, but external availability, credentials, and execution capacity still apply. Reconstructed context is not exact native-session restoration, tool rollback, or exactly-once external execution. Closing releases execution resources while retaining recovery; thread deletion writes permanent recovery tombstones, including unloaded children. A provider may lack native child transcript attribution, individual cancellation, or steering. Capability checks must remain truthful. Native children sharing one MCP credential cannot be distinguished from their nearest identifiable owner; this affects hierarchy and control authorization.

User-facing behavior and the reusable instruction block live in [cross-provider agents](../user/cross-provider-agents.md).
