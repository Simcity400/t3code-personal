# Task observability

The server owns a current `TaskState` for each provider task. Agents and background work use the same identity, ownership, status, usage, and stop-capability model. The orchestration decider applies each task lifecycle activity to its previous state, then commits a `task.state` activity with a stable thread/task key in the same event batch. The existing activity projection upserts that record; no separate task table is required. Cross-provider restart reconciliation adds partial indexes over current task and request records.

Snapshots pin current task records independently of turn windows and work-log retention. Instructions and native collaboration tool records are retained as conversation history. Clients select current records and group them for presentation; they do not infer roster membership or reconstruct status from retained progress rows. Old threads are deliberately not backfilled. Every new task event establishes or updates a record.

A thin provider update inherits identity and ownership. Explicit task types classify agents versus background work at the server boundary. The first terminal timestamp is preserved, metadata may still enrich a settled task, and explicit reactivation clears the previous result and increments its run count. A workflow ending settles its remaining active members. Session stop, interruption, or failure persists interruption for native active tasks so reconnecting cannot revive their old status. Independently owned [cross-provider children](cross-provider-agents.md) are excluded from this parent-session cascade and settle from their own execution events.

Codex child conversation IDs remain separate from the root ID. Notifications received before explicit child registration are buffered (bounded to 256 notifications per conversation and 32 unresolved conversations); exhaustion logs a warning. Registration drains them through the child mapper. Memory-consolidation traffic stays excluded. A child final message is never synthesized into a parent reply; explicit provider result reports remain supported.

Individual stopping uses `thread.turn.interrupt` with a `taskId`. The decider validates thread ownership. The provider service routes to the adapter's optional `stopTask` method, without recovering a missing session. Claude calls SDK `stopTask`; Codex interrupts only the child's active turn; OpenCode aborts only an owned child session. Cursor, Grok, and Antigravity currently have no individual task-stop adapter operation. Visibility remains available wherever their protocols expose tasks, ownership, and transcripts; T3 cannot infer processes or transcripts the provider does not expose.

Task stop receipts use one stable activity per task. A timeout or failure produces feedback without invoking the whole-session recovery path. Provider lifecycle events, rather than optimistic UI changes, determine when a task actually stops.

Web and desktop use `MessagesTimeline` for both transcripts. Mobile uses `ThreadFeed` for both, including earlier-turn pagination. Both show owner groups, workflow phases, run counts, and usage. Task-control lookup is indexed once per panel update, not scanned per row.
